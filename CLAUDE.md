# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Azangara Mods is a website for sharing custom levels for the game Azangara. Two projects live side by side:

- `AzangaraMods-Website-Back/`: ASP.NET Core (.NET 10) REST API with EF Core on PostgreSQL.
- `AzangaraMods-Website-Front/`: Next.js 16 (App Router, React 19, Turbopack) frontend. It has its own `CLAUDE.md`/`AGENTS.md`: this Next.js version has breaking changes compared with older releases, so read the relevant guide in `AzangaraMods-Website-Front/node_modules/next/dist/docs/` before writing frontend code.
- `libs/AzangaraTools/`: git submodule (github.com/Piripe/AzangaraTools) referenced by the backend for parsing Azangara `.pak` archives and level scripts. Run `git submodule update --init` before building the backend.

## Commands

The whole stack (Postgres, backend on :8080, frontend dev server on :3000) runs through Docker Compose. `compose.yaml` is gitignored because it holds real secrets; copy it from `compose.yaml.example`.

```sh
docker compose up --build          # full stack
docker compose up -d --build azangaramodswebsiteback   # rebuild the API after backend changes
```

The frontend container bind-mounts `AzangaraMods-Website-Front/` and runs `next dev`, so frontend edits hot-reload. **Do not start a second `next dev` on the host**: both would share and corrupt `.next/dev`.

Frontend (run in `AzangaraMods-Website-Front/`):
```sh
npm run lint     # eslint
npm run build    # production build (also type-checks)
```
Environment comes from `.env` (see `.env.example`): `NEXT_PUBLIC_API_URL` is the backend base URL.

Backend:
```sh
dotnet build AzangaraMods-Website-Back.sln
dotnet ef migrations add <Name> --project AzangaraMods-Website-Back
```
Migrations are applied automatically at startup (`Database.Migrate()` in `Program.cs`). The connection string in `appsettings*.json` points to host `db`, which is the compose service name. Env vars the backend reads: `FRONT_URL` (CORS origin), `DOWNLOAD_URL`, `DISCORD_WEBHOOK`, `DISCORD_EMOTES`, `DISCORD_ADMIN_WEBHOOK` (optional, notified when a level verification is requested), `DATA_DIR` (defaults to `/data`).

This repository has no test suite. The only tests are in the submodule (`libs/AzangaraTools/AzangaraTools.Tests`).

## Backend architecture

- **Auth**: Every request goes through `Middlewares/AuthMiddleware.cs`, which validates the `Authorization` header (a raw base64 token, with no `Bearer` prefix; the format is in `TokenService`). Endpoints return 401 unless they are tagged `[Public]` (`Attributes/PublicAttribute.cs`). The authenticated user is stored in `HttpContext.Items[0]`, and controllers read it as `(HttpContext.Items[0] as User)`. On `[Public]` endpoints the value can be null when the caller is anonymous. Endpoints tagged `[Admin]` (`Attributes/AdminAttribute.cs`) return 403 unless the user has `UserFlags.Admin`. Level ownership checks go through `ILevelService.UserCanEditLevel`, which also lets admins through. A user who disables their account gets `UserFlags.Disabled`: their tokens are revoked, and their levels, downloads, avatar and Discord posts are treated as unpublished until they log in again, which clears the flag. Public queries must filter on it (see `LevelService.SearchLevels`).
- **Layering**: Controllers use primary-constructor DI and call scoped services (`Services/<Area>/I<Area>Service` + implementation, registered in `Program.cs`), and the services use `MainDbContext`. Responses are mapped to DTOs in `Models/Dto` with AutoMapper. Every map is declared in `Program.cs`, so a new DTO needs a `CreateMap` there.
- **Errors**: Failures return `ErrorResponseModel(message, ErrorCodes.X)`. `Enums/ErrorCodes.cs` is mirrored by hand in `AzangaraMods-Website-Front/src/enums.ts`, so update both when you add a code. The same goes for `LevelDifficulties`.
- **IDs**: All entity IDs are `long` values from `IdUtils.GenerateId()`, which is time-based and Snowflake-like. They are not generated by the database. They are serialized as strings to the frontend (see `src/index.d.ts`).
- **File storage**: Uploaded level files and gallery images are stored on disk, not in the DB, at a sharded path derived from the entity ID (`FileUtils.GetIdFilePath`, under `DATA_DIR`). Level uploads (`.pak` or `.zip`) go through `LevelFileService.ProcessLevelFile`, which normalizes path casing and parses them with AzangaraTools. Gallery images are processed with Magick.NET. Files are served by `DownloadController` (`/download/...`), which also counts downloads behind the in-memory `RateLimiter`.
- **Reports and site settings**: anyone can report a level file (`POST /levels/{id}/files/{fileId}/reports`, `[Public]`) unless an admin turns on `SiteSettings.ReportsRequireAccount`. `SiteSettings` is a single-row table (seeded by its migration) read through `ISiteSettingsService`, exposed publicly at `GET /settings` and changed at `PATCH /admin/settings`. New reports are posted to `DISCORD_ADMIN_WEBHOOK` and reviewed in the Reports tab of the admin panel (`Controllers/Admin/ReportsController.cs`).
- **Discord**: `DiscordService` posts and updates a webhook message per published level (download counts and star emotes from `DISCORD_EMOTES`). Admin endpoints in `Controllers/Admin/` rebuild these messages or reprocess level files.

## Frontend architecture

- Client-side auth: `context/UserContext.tsx` keeps the token in `localStorage` and loads `/users/@me`. Components use it through `hooks/useUserData`.
- Every API call goes through `utils/fetchApi(path, token, method, body, contentType)`. Pass `contentType = null` for `FormData` uploads.
- Shared API types are global ambient types in `src/index.d.ts` (`User`, `Level`, `LevelFile`, …) and must match the backend DTOs.
- `components/kit/` is the in-house UI kit (buttons, fields, popups, tags input, …), styled with CSS Modules. Popups render into the `#portal` div declared in the root layout. Build pages from kit components rather than writing new styles.
- Routes: `/` is the landing page. `/levels` is the public level browser (search, difficulty/tag filters, sort and page all live in the URL query and are forwarded to `GET /levels`), and `/levels/[id]` is the level page (description, gallery, versions, downloads). The level's author also manages it there (edit, upload files and screenshots, publish or submit for review, delete), and admins get edit, approve/reject and delete. `/dashboard/levels` lists the user's levels, and `/dashboard/levels/new` and `/dashboard/levels/[id]/edit` hold the level forms. `/dashboard/admin` is the admin panel (every level including drafts; publish, reprocess files, refresh Discord posts, delete; plus a Reports tab, opened by `?tab=reports`), backed by `Controllers/Admin/`. `/dashboard/settings` is the account settings page (username, profile picture, email, password, sessions, GDPR data export, disable/delete account), backed by `Controllers/UserSettingsController.cs` under `/users/@me/...`.
